Variables, types et conversions

Une variable donne un nom à une valeur. Le type indique les opérations possibles. Les données lues dans un fichier arrivent souvent sous forme de chaînes.

Les types courants

  • str : texte, ex. "45.76"
  • int : entier, ex. 12
  • float : nombre décimal, ex. 45.76
  • bool : True ou False
  • list : collection ordonnée
types.py
heure = "12:55:35"       # str
nb_lignes = 120          # int
latitude = float("45.76")
fichier_valide = True

print(type(heure))
print(latitude + 1.0)

# int("bonjour") -> ValueError
À retenir : convertir explicitement avec int(), float() ou str(). Une conversion peut échouer : anticipez les données mal formées.

Manipuler du texte comme un analyste

Nettoyer et découper

strings.py
ligne = "  ALERT,192.0.2.8\\n"
propre = ligne.strip()
champs = propre.split(",")

print(propre)
print(champs[0])  # ALERT

strip() enlève les espaces et retours en bordure. split() découpe une chaîne selon un séparateur.

Tester, boucler, filtrer

filter.py
evenements = [
    "LOGIN_OK",
    "LOGIN_FAILED",
    "LOGOUT"
]

for event in evenements:
    if "FAILED" in event:
        print(event)

Une condition choisit le chemin d'exécution. Une boucle répète une action pour chaque élément.

Attention : split(',') ne comprend pas à lui seul les champs CSV contenant des virgules entre guillemets. Pour un vrai CSV, préférez le module standard csv.

09 · Gestion des erreurs
09

Ne pas laisser une donnée inattendue arrêter l'analyse

Conversion contrôlée

conversion.py
texte = "12.5"

try:
    mesure = float(texte)
except ValueError:
    print("Mesure invalide")
else:
    print("Mesure :", mesure)

Pièges à connaître

  • float("abc") déclenche ValueError.
  • float("nan") produit un NaN : ce n'est pas une erreur de conversion.
  • math.isnan(x) détecte NaN.
  • float("inf") est aussi accepté : pensez à math.isfinite().
Un choix métier doit être explicite : ignorer une ligne, la mettre en quarantaine ou remplacer une valeur ? Un zéro GPS peut être une vraie coordonnée. Ne le choisissez comme valeur de secours que si le cahier des charges le demande.
10 · Git · introduction

Git : mémoire, collaboration et traçabilité du code

Git est un système de gestion de versions distribué. Il conserve l'historique des changements d'un projet et permet de revenir à un état antérieur.

Pourquoi en cybersécurité ?

  • Historique : comprendre quand le script a changé.
  • Revue : comparer et relire les modifications.
  • Reproductibilité : retrouver une version du code.
  • Collaboration : branches, pull requests et validation.
  • CI/CD : déclencher des tests sur des changements.

Les commandes essentielles

terminal
git init
git status
git add parse_gps.py
git commit -m "Ajoute le parseur GPS"
git log --oneline
git diff

add prépare les changements ; commit enregistre un instantané dans l'historique local.

Nuance importante : Git seul ne prouve pas l'identité réelle de l'auteur ni la valeur juridique d'un artefact. Les signatures, les contrôles d'accès, les journaux et la procédure de conservation sont complémentaires.

Signer ses commits avec une clé SSH

Un commit signé apporte une preuve cryptographique liée à une clé (non-répudiation) et active le badge Verified sur GitHub.
Nuance : Il ne prouve pas à lui seul l'identité réelle de son détenteur ni la véracité du contenu.

terminal · créer la clé si nécessaire
ssh-keygen -t ed25519 -C "votre_email@example.com"

git config --global user.name "Votre Nom"
git config --global user.email "votre_email@example.com"
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true

cat ~/.ssh/id_ed25519.pub

Sur GitHub

  1. Ouvrir Settings → SSH and GPG keys.
  2. Choisir New SSH key.
  3. Choisir le type de clé « Signing Key ».
  4. Coller le contenu de la clé publique.
  5. Créer un commit signé et vérifier son statut.

Vérifications

terminal
git config --get gpg.format
git config --get user.signingkey
git log --show-signature -1
git commit -S -m "Teste la signature"

La clé privée reste sur votre machine : ne la publiez jamais et ne la transmettez pas au dépôt.

14 · Cahier des charges
14

Transformer les consignes en règles testables

Extraction & normalisation

  • Ne retenir que les lignes correspondant aux marqueurs prévus.
  • Récupérer date, heure, latitude et longitude, y compris dans les formats documentés.
  • Supprimer les microsecondes : hh:mm:ss.
  • Arrondir les coordonnées conservées à deux décimales.
  • Compléter les coordonnées manquantes/corrompues avec +0.000000 si la règle métier l'exige.

Qualité & dédoublonnage

  • Écarter les NaN et les valeurs non finies selon la politique définie.
  • Ne pas exporter l'index source comme colonne métier.
  • Supprimer les doublons géographiques avec la tolérance définie.
  • Produire un CSV stable et documenté.
  • Tester les cas limites et rendre les choix explicites.
Point à clarifier avant de coder : « doublons à ±1° » signifie-t-il comparer chaque point à tous les points conservés, ou regrouper des points par zone ? Cette règle n'est pas une simple égalité et peut supprimer des positions légitimes. La faire valider par l'enseignant.

16 · Étape 2 du TP
16

Extraire les champs sans supposer que tout est propre

Avant de lire des indices comme parts[2], vérifier que la ligne contient assez de champs. Pour le format CSV avec champs entre guillemets, utiliser csv.reader plutôt qu'un simple découpage par virgules.

démonstration · module csv
import csv

ligne = (
    '1176,2019/10/25,12:55:35.357444,'
    '"45.76, 4.83",GNSS_ACCESS_LIB'
)

champs = next(csv.reader([ligne]))
print(champs[2])  # 12:55:35.357444
print(champs[3])  # 45.76, 4.83

À faire dans votre fonction

  • Définir le format attendu pour chaque marqueur.
  • Vérifier le nombre de champs avant tout accès par index.
  • Convertir les nombres dans un bloc try/except.
  • Ne pas confondre chaîne vide, NaN et zéro.
  • Décider comment signaler une ligne impossible à parser.
Le second format Trip Data | Start | Latitude: peut être structuré différemment du CSV d'exemple. Il faut examiner des lignes réelles représentatives avant de choisir le parseur.
17 · Étape 3 du TP
17

Nettoyer les valeurs et contrôler les limites

Contrôler une coordonnée

validation.py · exemple autonome
import math

def convertir_mesure(texte):
    try:
        valeur = float(texte.strip())
    except ValueError:
        return None

    if not math.isfinite(valeur):
        return None

    return valeur

Cette fonction renvoie None pour une valeur illisible ou non finie. À vous de décider comment le TP doit traiter ce cas.

Tests à prévoir

  • Nombre valide : "45.76"
  • Espaces : " 4.83 "
  • Champ vide : ""
  • NaN : "nan"
  • Texte : "inconnu"
  • Latitude hors de [-90, 90] ou longitude hors de [-180, 180]
Important : si le cahier des charges impose une valeur de remplacement, documentez la règle et conservez si possible un compteur des valeurs corrigées. En forensic, les corrections ne doivent pas être invisibles.
18 · Étape 4 du TP
18

Dédoublonnage : écrire une règle non ambiguë

Arrondir à deux décimales réduit la précision. Une tolérance de ±1° est beaucoup plus large que l'arrondi et représente une distance géographique importante : testez son effet avant de l'appliquer.

Logique à implémenter

  1. Créer une liste de positions retenues.
  2. Pour chaque position candidate, la comparer aux positions retenues.
  3. Appliquer la règle de tolérance validée.
  4. Garder ou rejeter la position, de façon déterministe.

Question de conception

Si A est proche de B, et B proche de C, mais A pas proche de C, faut-il garder A et C ? La réponse dépend de la règle de regroupement.

pseudo-code · à compléter
for point in points:
    doublon = False
    # TODO : comparer point aux points retenus
    # TODO : appliquer la tolérance décidée
    if not doublon:
        points_retenus.append(point)
Le filtrage par latitude/longitude séparées ne mesure pas une distance exacte. Pour une analyse géographique rigoureuse, utilisez une distance géodésique adaptée et justifiez le seuil.

20 · Intégrité · SHA-256
20

Calculer une empreinte du fichier exporté

SHA-256 calcule une empreinte du contenu exact d'un fichier. Une modification, même minime, change généralement l'empreinte. Pour comparer des empreintes, il faut comparer le même fichier octet pour octet.

hash_csv.py
import hashlib

def sha256_fichier(chemin):
    h = hashlib.sha256()
    with open(chemin, "rb") as fichier:
        for bloc in iter(
            lambda: fichier.read(65536), b""
        ):
            h.update(bloc)
    return h.hexdigest()

empreinte = sha256_fichier("output_cleaned.csv")
print("SHA-256 :", empreinte)
print("Identifiant pédagogique :", empreinte[:12])

Ce que le hash prouve — et ne prouve pas

  • ✔ Permet de détecter si le contenu comparé a changé.
  • ✔ Permet de vérifier que deux copies sont identiques.
  • ✘ Ne prouve pas qui a créé le fichier.
  • ✘ Ne prouve pas que les données source étaient exactes.
  • ✘ Ne remplace pas la chaîne de conservation des preuves.
Pour les gros fichiers, lire par blocs évite de charger tout le contenu en mémoire. Le préfixe du hash sert ici d'identifiant pédagogique, pas de mécanisme de sécurité autonome.

22 · DevSecOps · CI/CD
22

La pipeline teste le projet à chaque changement

TRIGGERPush ou pull request vers main/master.
ENVIRONNEMENTUn runner Ubuntu récupère le code.
EXÉCUTIONPython lance le parseur et génère le CSV.
VALIDATIONLe workflow vérifie le fichier et calcule SHA-256.

Pourquoi automatiser ?

  • Détecter tôt les régressions.
  • Exécuter les mêmes étapes sur un environnement propre.
  • Afficher clairement les échecs dans les logs.
  • Réduire les validations manuelles répétitives.

Le workflow n'est pas magique

  • Le fichier d'entrée doit être disponible au runner.
  • Les dépendances doivent être déclarées.
  • Le script doit retourner un code d'erreur en cas d'échec.
  • Une empreinte calculée n'est pas, à elle seule, une validation de la qualité des données.

Créer le fichier .github/workflows/main.yml

Placez le workflow dans le dépôt. Il s'exécute sur les push et pull requests vers main/master, échoue si le fichier d'entrée ou le CSV manque, puis affiche l'empreinte et un identifiant court.

.github/workflows/main.yml
name: Validation OCLCC Pipeline CI/CD

on:
  push:
    branches: ["main", "master"]
  pull_request:
    branches: ["main", "master"]

jobs:
  validate-investigation:
    runs-on: ubuntu-latest
    steps:
      - name: Récupération du code source
        uses: actions/checkout@v4

      - name: Configuration de Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"

      - name: Exécution du parseur DFIR
        run: |
          test -f input_log.txt || {
            echo "Erreur : input_log.txt introuvable"; exit 1;
          }
          python parse_gps.py

      - name: Vérifier le CSV et calculer SHA-256
        run: |
          test -f output_cleaned.csv || {
            echo "Erreur : CSV non généré"; exit 1;
          }
          HASH=$(sha256sum output_cleaned.csv | awk '{print $1}')
          echo "SHA-256 : $HASH"
          echo "Identifiant pédagogique : FLAG_OCLCC_${HASH:0:12}"
Le nom FLAG_OCLCC_… est une convention d'exercice, pas une preuve d'enquête. Les caractères spéciaux YAML comme on sont valides dans un workflow GitHub Actions.

Quand la pipeline échoue : enquêter méthodiquement

ERREUR

Fichier introuvable

Vérifier le nom, la casse, le chemin relatif et le contenu réellement présent dans le dépôt distant.

ERREUR

Conversion invalide

Identifier la ligne fautive, contrôler le format d'entrée et décider d'une politique de rejet ou de correction.

ERREUR

CSV non généré

Vérifier l'appel d'export, le chemin de sortie, les droits et le code de sortie du script.

Checklist de validation

□ Le script fonctionne localement sur une copie de test.

□ Le CSV a un en-tête stable et aucune colonne d'index.

□ Les cas vides et mal formés sont testés.

□ Le workflow est au bon emplacement.

□ La pipeline est verte sur le dépôt distant.

□ Le hash affiché correspond au CSV généré.
